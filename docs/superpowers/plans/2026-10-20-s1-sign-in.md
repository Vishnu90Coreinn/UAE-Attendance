# S1 — Sign In and Role Guard

**Goal:** Users can sign in, see who they are, change their own password and sign out; every API endpoint requires a signed-in user unless explicitly marked anonymous; roles are enforced on the server.

**Branch:** `slice/s1-sign-in` (stacked on `slice/s0-walking-skeleton`, which is not yet merged).
**Master plan:** `2026-10-19-hr-payroll-vertical-slices.md` (slice S1, decisions D2/D5, roles matrix C6). **UI rules:** `docs/design-system.md` (ui-ux-pro-max) — mandatory for every UI task.

This is a compact spec, not a verbatim-code plan. Each task is done test-first by one implementer, who writes the code to the interfaces and rules below. Conventions from S0 still apply (xUnit against real SQL Server via `TestDatabase`/`ApiFactory`, Vitest, file creation with the Write tool, commit messages end with the co-author trailer, no push).

## Demo

Log in as the seeded Administrator, see `Logged in as <user> (<role>)` in the header, change the password, log out. Five wrong passwords lock the account for 15 minutes. A Viewer token gets 403 on an Administrator endpoint; no token gets 401 everywhere except health and login.

## Rules (the specification)

| # | Rule |
|---|------|
| A1 | Roles are exactly `Administrator`, `HR Staff`, `Viewer` (constants in `Auth/Roles.cs`). Policies: `AnyUser` (authenticated), `HrOrAdmin`, `AdminOnly` (`Auth/Policies.cs`) |
| A2 | **Secure by default:** `FallbackPolicy` requires an authenticated user. Only `POST /api/auth/login` and `GET /api/health` carry `[AllowAnonymous]`. Unknown routes stay 404 |
| A3 | Login: username matched case-insensitively. Unknown user, wrong password and inactive user all return the same `401` problem ("Invalid username or password.") and, for unknown users, a dummy hash verification is still performed so timing does not reveal existence |
| A4 | Lockout: 5 consecutive failures lock the account for 15 minutes (`LockoutEndUtc`). While locked, the password is not checked and the API returns `423 Locked` ("Account temporarily locked. Try again later."). A success resets `FailedLoginCount` to 0 and clears the lockout. An expired lockout behaves as unlocked |
| A5 | Login success response: `{ token, expiresUtc, user: { id, username, role } }`. Token: HS256 JWT, 8-hour lifetime (`Jwt:ExpiryHours`), claims `sub` (user id), name (username), role; issuer/audience from config; 1-minute clock skew |
| A6 | `Jwt:Key` must be at least 32 characters, from configuration (`Jwt__Key` environment variable); the API refuses to start otherwise. `appsettings.Development.json` holds a clearly labelled development-only key; production must set the variable |
| A7 | Passwords: hashed with `PasswordHasher<User>` (PBKDF2); never stored, logged or returned. Policy: 10–128 characters and not equal to the username (case-insensitive) |
| A8 | `GET /api/auth/me` returns `{ id, username, role }` for the current token's user, read from the database (404-safe: a deleted user gets 401) |
| A9 | `POST /api/auth/change-password` `{ currentPassword, newPassword }`: wrong current password → 400 with a field error on `currentPassword`; policy violation or new equals current → 400 field error on `newPassword`; success → 204, new hash saved, `PasswordChanged` audited |
| A10 | Login endpoint is rate limited per client IP (`RateLimiting:LoginPerMinute`, default 10) → `429`. Behind a reverse proxy the real client IP needs forwarded-headers support: add in S8 |
| A11 | Audit rows (`AuditLogs`): `LoginSucceeded`, `LoginFailed` (actor = username attempted; details never contain a password), `AccountLocked`, `PasswordChanged`, `AdminSeeded`. Rows are written by `IAuditLogger.Write(...)`, which only *adds* to the context; the calling service calls `SaveChangesAsync` so the audit row commits with the change |
| A12 | First run: if `Users` is empty and `Seed:AdminUsername` + `Seed:AdminPassword` (env `Seed__AdminUsername`, `Seed__AdminPassword`) are set, create that Administrator (password must satisfy A7). If `Users` is empty and they are missing: in the Production environment the API refuses to start; in other environments it logs a warning and continues. If any user exists the seeder does nothing. No default password exists anywhere in the code |
| A13 | Client stores the token in memory and mirrors it to `sessionStorage`; on page load a stored token is validated with `GET /api/auth/me` and discarded if rejected. Any `401` from the API signs the user out. Logout clears both |

## Data model

`Users`: `Id` int identity PK · `Username` nvarchar(50), unique, case-insensitive collation · `PasswordHash` nvarchar(256) · `Role` nvarchar(20) with a CHECK constraint on the three role names · `IsActive` bit default 1 · `FailedLoginCount` int default 0 · `LockoutEndUtc` datetime2 null · `CreatedUtc` datetime2.
`AuditLogs`: `Id` bigint identity PK · `TimestampUtc` datetime2 · `ActorUsername` nvarchar(50) null · `Action` nvarchar(50) · `EntityType` nvarchar(50) null · `EntityId` nvarchar(50) null · `DetailsJson` nvarchar(max) null; index on `TimestampUtc`. No FK to `Users` (rows must survive user deletion).
One migration `AddUsersAndAuditLogs`.

## Backend structure (`apps/api`)

`Auth/Roles.cs`, `Auth/Policies.cs`, `Auth/JwtOptions.cs`, `Auth/JwtTokenService.cs`, `Auth/PasswordPolicy.cs` · `Data/Entities/User.cs`, `Data/Entities/AuditLog.cs` (+ EF configuration inside `AppDbContext`) · `Services/AuthService.cs`, `Services/AuditLogger.cs` (`IAuditLogger`), `Services/AdminSeeder.cs` · `Controllers/AuthController.cs` · `Dtos/Auth*.cs`. New package: `Microsoft.AspNetCore.Authentication.JwtBearer` (10.0.x, matching the other 10.0.13 packages). Middleware order: CorrelationId → request logging → ExceptionHandling → rate limiter → authentication → authorization → controllers.

Tests (`apps/api.tests`): a test-only `ProbeController` (routes `/api/_probe/any|hr|admin|unmarked`) registered through the factory so the role matrix can be tested before real endpoints exist; a `TestUsers` helper that inserts users with hashed passwords directly via `AppDbContext`.

## Frontend structure (`apps/web`)

`api/client.ts` (adds `apiPost`, `setAuthToken`, `setUnauthorizedHandler`, parses validation `errors` into `ApiError.fieldErrors`) · `api/auth.ts` · `contexts/AuthContext.tsx` (+ `useAuth`) · `features/auth/LoginPage.tsx`, `ProtectedRoute.tsx`, `ChangePasswordDialog.tsx` · `components/Layout.tsx` (header user block, logout, change-password button, role-filtered tabs) · `components/navItems.ts` (adds `roles`). New dependency: `lucide-react` (icons). Native `<dialog>` for the modal (built-in focus trap and Esc); polyfill `showModal`/`close` in `test-setup.ts` if jsdom lacks them.

UI rules for these screens (from `docs/design-system.md`): visible labels, autofocus first field, loading state on submit and a disabled button while pending, specific error text in a `role="alert"` region (never colour only), 44px targets, visible focus, Lucide icons with text or `aria-label`, no horizontal scroll at 375px, login card centred on `gray-100` with the company name above it.

## Tasks

1. **T1 — Tables, roles, audit logger.** Entities + config + migration; `Roles`, `Policies`; `IAuditLogger`. Tests: unique username is case-insensitive (`Admin` vs `admin` → `DbUpdateException`), role CHECK rejects `Boss`, audit logger adds a row that persists only after `SaveChangesAsync`, migrations still apply cleanly.
2. **T2 — JWT, login, `me`, policies, secure-by-default.** `JwtTokenService`, `AuthService.LoginAsync` (A3–A5, A11), `AuthController` login + me, Program.cs wiring (JwtBearer, authorization policies, fallback policy, `[AllowAnonymous]` on health), config keys (A6) and `ApiFactory` support for them, `ProbeController`, `TestUsers`. Tests: success, wrong password / unknown user / inactive give identical 401 bodies, lockout and reset (A4), `me` with/without token, role matrix over the probe routes (Viewer/HR/Admin × any/hr/admin; anonymous → 401 incl. `unmarked`; health still anonymous), token claims, short `Jwt:Key` refuses to start, audit rows written without passwords.
3. **T3 — Change password and login rate limit.** A7, A9, A10 plus `PasswordPolicy` unit tests; change-password endpoint tests; rate-limit test (login limit set low through config → 429).
4. **T4 — First-run admin seeder and configuration docs.** A12 with tests (empty DB + config creates a hashed Administrator and an `AdminSeeded` audit row; second run no-op; Production + empty + no config throws; short password throws; existing users untouched). Wire after migration in Program.cs. Update `.env.example` (`Jwt__Key`, `Seed__AdminUsername`, `Seed__AdminPassword`, `RateLimiting__LoginPerMinute`), `README.md` (first-run admin; use `dotnet user-secrets` for the dev admin password: add `UserSecretsId` to the csproj; sign-in steps) and `appsettings.json`/`appsettings.Development.json` defaults.
5. **T5 — Web auth plumbing and login page.** Client changes, `api/auth.ts`, `AuthContext` (A13), `LoginPage`, `ProtectedRoute`, routes (`/login` public; everything else inside `ProtectedRoute` + `Layout`). Vitest: client sends `Authorization` and parses field errors; unauthorized handler fires on 401; context login/logout/restore; login page submits, shows pending and error states; redirect to `/login` when signed out and back after sign-in.
6. **T6 — Role-aware shell and change-password dialog.** Layout header (`Logged in as <user> (<role>)`, change-password, logout with Lucide icons), role-filtered tabs (`User Manager` visible to Administrator only), `ChangePasswordDialog` (client checks: ≥10 chars and confirmation match; server `fieldErrors` shown under fields; success message and close). Tests for all of the above plus dialog Esc/focus behaviour.
7. **T7 — End-to-end check and final verification.** Real run: API + web, sign in as the seeded admin, change password, log out, lockout after 5 failures (API call), Viewer 403 against a protected route is covered by tests; check desktop and 375px, console clean; full build/test/lint/build; update the memory note.

**Definition of done:** all tests written first and seen failing; `dotnet build` 0 warnings; API and web suites green; browser walkthrough clean; no password, token or hash in any log line or API response (checked by tests where practical); branch pushed only when asked.
